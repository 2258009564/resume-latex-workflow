# 从参考简历改写项目

用户说“对着这个改”“参考他的项目”时，必须实际读到参考的项目和技能段。先列出可迁移的写法：系统目标、组件关系、每条职责的技术密度、哪些词被加粗、技能如何合并；再映射到当前候选人的内容。不能只取排版，沿用原来基础的项目文案。

## 内容模式

事实投递稿以已有实现、结果为边界。明确的目标稿可以按用户希望补全的能力直接写成职责句；不要再次追问已授权的能力是否实现，也不要在用户要求干净正文时插入待学习/待核实标签。把来源和完成情况留在工作区或既有说明中，避免正文和评估状态混淆。目标稿同样不编造性能数字、测试成绩、奖项或工作履历。

## 职责深度

每条采用“问题或目标→方法与关键机制→约束/作用”。例如分布式KV可从多组架构、日志追赶、一致性语义、快照恢复、分片迁移、调度中挑3～5条；不要求全部写，也不默认某个项目必须有全部功能。

- 快速回溯应解释利用冲突任期/索引跳跃定位，不能无条件写成从 O(N) 降到 O(1)。
- 一致读应区分权威确认与应用进度；请求去重需覆盖回复丢失、换主及恢复，不把日志索引当成逻辑请求ID。
- 快照应说明业务状态、去重信息、配置/应用边界与日志后缀的关系，而非只写支持Snapshot。
- 分片迁移应说明版本、状态、所有权交接与回收，不从并行组自动推导所有请求零停机。
- Leader均衡与副本/分片均衡是不同动作。迁主应选择已追平的投票副本并考虑超时、调度冷却和并发控制；Learner可作为独立扩展，不为堆词硬塞进每份简历。

以上是写作检查例子，实际技术事实仍以官方规范及相应项目为准。相同原则也适用于缓存、消息、Web等项目：写清成功边界、重复执行、错误处理及资源约束，不把“使用工具”自动包装为“达成收益”。

## 视觉与技能

借鉴“概述＋职责”及句内重点，不复制他人信息和整段文字。单条挑出关键机制与可证明结果加粗，常规字体与强调字体保持用户指定风格，渲染后确认对比。参考中的专业技能若能把网络、操作系统、算法与工程分析串成一个能力段，可采用这种组织方式，不引入对方独有的SDK、监控平台、微服务组件或熟练度。

技术写作校验可从[Raft 原论文](https://raft.github.io/raft.pdf)、[etcd Raft 原始实现](https://github.com/etcd-io/raft)、[Learner 设计](https://etcd.io/docs/v3.5/learning/design-learner/)及[PD 调度实践](https://docs.pingcap.com/tidb/stable/pd-scheduling-best-practices/)查起；这些是机制来源，不是候选人完成记录。
